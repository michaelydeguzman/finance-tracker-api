## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Use two separate tables — `RecurringTransactions` (template) and the existing `Transactions` (instances). No discriminator columns, no TPH.
- **D-02:** `Transaction` gets a nullable `RecurringTransactionId` FK pointing back to its template. A transaction with `RecurringTransactionId = null` is a standalone one-off transaction.
- **D-03:** Template entity fields: `Id` (Guid, PK), `Name` (required, MaxLength 250), `Description` (optional, MaxLength 500), `DefaultAmount` (decimal), `CategoryId` (Guid, FK → Category), `FrequencyId` (Guid, FK → Frequency), `StartDate` (DateTime), `EndDate` (DateTime?), `NextOccurrenceDate` (DateTime), `Status` (enum: Active/Paused/Cancelled), `CreatedAt` (DateTime), `CreatedBy` (string)
- **D-04:** `DefaultAmount` is the template-level default. Individual `Transaction.Amount` is the per-instance value (no separate override column on Transaction).
- **D-05:** `RecurringTransactionStatus` enum: `Active`, `Paused`, `Cancelled`. No `Completed` state.
- **D-06:** `NextOccurrenceDate` stored on the template; background service (Phase 4) reads and advances it.
- **D-07:** `Frequency` lookup table retained as-is. `RecurringTransaction.FrequencyId` is a required FK to `Frequency`. No changes to the `Frequency` entity data in this phase.
- **D-08:** `Transaction.FrequencyId` is removed. Frequency information belongs on the template, not individual instances.
- **D-09:** Existing `Transaction` rows with `FrequencyId` set are converted to standalone: `FrequencyId` nulled out in migration data step, then the column and its FK/index are dropped.
- **D-10:** No `RecurringTransaction` templates are auto-created from existing data.

- EF Core configuration details (index strategy, cascade delete behavior on `RecurringTransactionId` FK)
- Exact migration sequencing (null-out data → drop FK → add new table → add FK on Transaction)
- Navigation property naming conventions

- Generation service logic → Phase 4
- Pause/cancel/skip lifecycle actions → Phase 5
- Calendar-based frequency interval calculations → Phase 3

## Summary

This phase introduces a new `RecurringTransaction` entity as a template master record and restructures the `Transaction` entity to reference it via a nullable FK. The existing `Transaction.FrequencyId` FK is being removed — frequency belongs on the template, not the instance. The primary work is: (1) add a new domain entity + enum, (2) modify the existing Transaction entity, (3) update EF Core configurations, (4) generate a migration that performs a data nulling step before schema changes, and (5) clean up all application-layer references to `Transaction.FrequencyId`.

The codebase is a clean layered architecture (Domain → Application → Infrastructure → API) with EF Core 8.0.0 + SQL Server, xUnit integration tests, and MediatR-based command/query handlers. There are **7 application-layer files** that reference `Transaction.FrequencyId` and must be updated in addition to the domain/infrastructure changes.

**Primary recommendation:** Follow the exact established patterns (Guid PKs, `IEntityTypeConfiguration<T>` per entity, enum stored as string, `CreatedAt`+`CreatedBy` audit fields). The migration requires one manually added raw SQL statement at the top of `Up()` for the data nulling step; everything else is auto-generated by EF Core tooling.

## Architecture Patterns

### Existing Conventions to Follow

1. **Enum + entity in one file** — `FrequencyType` lives in `Frequency.cs`; `CategoryType` lives in `Category.cs`. Therefore `RecurringTransactionStatus` lives in `RecurringTransaction.cs`.

2. **Entity structure** — All entities use `[Key]` attribute on Guid PK, data annotation constraints (`[Required]`, `[MaxLength]`), explicit FK properties alongside navigation properties (e.g. `CategoryId` + `Category`), and `CreatedAt` + `CreatedBy` audit fields.

3. **Required navigation properties** — Non-nullable navigations use `required` keyword: e.g. `public required Category Category { get; set; }`. Nullable navigations do NOT use `required`: e.g. `public Frequency? Frequency { get; set; }`.

4. **EF Core configuration** — One `IEntityTypeConfiguration<T>` file per entity in `FinanceTracker.Infrastructure/Persistence/Configurations/`. Auto-discovered via `modelBuilder.ApplyConfigurationsFromAssembly()` — no manual registration needed.

5. **Enum stored as string** — `builder.Property(e => e.SomeEnum).IsRequired().HasConversion<string>()` (pattern used for `FrequencyType` and `CategoryType`).

6. **Decimal precision** — `builder.Property(e => e.Amount).IsRequired().HasPrecision(18, 2)` (existing `Transaction.Amount` pattern).

7. **Indexes** — Explicit per-column indexes via `builder.HasIndex(e => e.ColumnName)` in the configuration file.

### Pattern 1: New Entity File (RecurringTransaction.cs)

using System.ComponentModel.DataAnnotations;

namespace FinanceTracker.Domain.Entities
{
    public enum RecurringTransactionStatus
    {
        Active,
        Paused,
        Cancelled
    }

    public class RecurringTransaction
    {
        [Key]
        public Guid Id { get; set; }

        [Required]
        [MaxLength(250)]
        public string Name { get; set; } = string.Empty;

        [MaxLength(500)]
        public string? Description { get; set; }

        public decimal DefaultAmount { get; set; }

        [Required]
        public required Guid CategoryId { get; set; }
        public required Category Category { get; set; }

        [Required]
        public required Guid FrequencyId { get; set; }
        public required Frequency Frequency { get; set; }

        public DateTime StartDate { get; set; }

        public DateTime? EndDate { get; set; }

        public DateTime NextOccurrenceDate { get; set; }

        [Required]
        public RecurringTransactionStatus Status { get; set; }

        public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

        public string CreatedBy { get; set; } = string.Empty;

        // Navigation: instances generated from this template
        public ICollection<Transaction> Transactions { get; set; } = new List<Transaction>();
    }
}

### Pattern 2: EF Core Configuration (RecurringTransactionConfiguration.cs)
```csharp
using FinanceTracker.Domain.Entities;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace FinanceTracker.Infrastructure.Persistence.Configurations
{
    public class RecurringTransactionConfiguration : IEntityTypeConfiguration<RecurringTransaction>
    {
        public void Configure(EntityTypeBuilder<RecurringTransaction> builder)
        {
            builder.HasKey(e => e.Id);

            builder.Property(e => e.Name)
                .IsRequired()
                .HasMaxLength(250);

            builder.Property(e => e.Description)
                .HasMaxLength(500);

            builder.Property(e => e.DefaultAmount)
                .IsRequired()
                .HasPrecision(18, 2);

            builder.Property(e => e.StartDate)
                .IsRequired();

            builder.Property(e => e.NextOccurrenceDate)
                .IsRequired();

            builder.Property(e => e.Status)
                .IsRequired()
                .HasConversion<string>();

            builder.Property(e => e.CreatedAt)
                .IsRequired();

            builder.HasOne(e => e.Category)
                .WithMany(c => c.RecurringTransactions)
                .HasForeignKey(e => e.CategoryId)
                .OnDelete(DeleteBehavior.Restrict);

            builder.HasOne(e => e.Frequency)
                .WithMany(f => f.RecurringTransactions)
                .HasForeignKey(e => e.FrequencyId)
                .OnDelete(DeleteBehavior.Restrict);

            builder.HasMany(e => e.Transactions)
                .WithOne(t => t.RecurringTransaction)
                .HasForeignKey(t => t.RecurringTransactionId)
                .OnDelete(DeleteBehavior.SetNull);

            builder.HasIndex(e => e.CategoryId);
            builder.HasIndex(e => e.FrequencyId);
            builder.HasIndex(e => e.Status);
        }
    }
}
```

### Pattern 5: Migration with Manual Data Step
After running `dotnet ef migrations add`, manually insert the data nulling step at the **top** of `Up()`:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    // D-09: Null out existing FrequencyId values — existing transactions become standalone
    migrationBuilder.Sql(
        "UPDATE [Transactions] SET [FrequencyId] = NULL WHERE [FrequencyId] IS NOT NULL");

    // ... EF Core auto-generated DDL follows (drop FK, drop index, drop column,
    //     create RecurringTransactions table, add RecurringTransactionId column, etc.)
}
```

### Anti-Patterns to Avoid

- **Configuring the HasMany/WithOne relationship in TransactionConfiguration** — do NOT add a `HasOne(t => t.RecurringTransaction).WithMany(...)` call in `TransactionConfiguration`. Configure bidirectional relationships from ONE side only (from `RecurringTransactionConfiguration`) to avoid conflicting configurations.
- **Using `required` keyword on nullable navigation properties** — `Transaction.RecurringTransaction` is `RecurringTransaction?` (nullable, no `required`). Only non-nullable required navigations use `required`.
- **Storing the enum as int** — always use `HasConversion<string>()` to match the established pattern and maintain human-readable DB values.
- **Forgetting the data step in the migration** — EF Core tooling does NOT automatically add `UPDATE ... SET FrequencyId = NULL`. This must be added manually at the top of `Up()`.
- **Removing the raw SQL data step in `Down()`** — the `Down()` method should restore the schema but cannot restore original FrequencyId values; this is acceptable and should be documented with a comment.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Bidirectional FK relationship config | Manual FK constraint via SQL | EF Core `HasOne`/`HasMany` | Handles constraint naming, cascade rules, index creation |
| Raw SQL data migration | Custom migration script | `migrationBuilder.Sql()` inside `Up()` | Runs atomically in the same migration transaction |
| Enum DB storage | Custom value converter | `.HasConversion<string>()` | Built-in EF Core, zero boilerplate, human-readable |
| Decimal precision | Raw SQL column type | `.HasPrecision(18, 2)` | EF Core generates `decimal(18,2)` column correctly |

## Common Pitfalls

### Pitfall 1: Relationship configured from both sides
**What goes wrong:** Configuring `HasOne(t => t.RecurringTransaction).WithMany(...)` in `TransactionConfiguration` AND `HasMany(e => e.Transactions).WithOne(...)` in `RecurringTransactionConfiguration` causes EF Core to create duplicate shadow FK properties or fail with a model validation error.
**Why it happens:** EF Core allows both sides of a relationship to be configured but expects them to reference the same relationship. Having two independent calls creates two separate relationships.
**How to avoid:** Configure the relationship from exactly ONE side — from `RecurringTransactionConfiguration` using `HasMany(...).WithOne(...).HasForeignKey(...)`. Remove any `HasOne` for this relationship from `TransactionConfiguration`.
**Warning signs:** EF Core throws `InvalidOperationException` during model building, or generates a migration with an unexpected extra FK column.

### Pitfall 2: Forgetting to update Frequency entity's nav property
**What goes wrong:** `Frequency.cs` currently has `public ICollection<Transaction> Transactions { get; set; }`. When `Transaction.FrequencyId` is removed, `TransactionConfiguration` no longer has `.WithMany(f => f.Transactions)`. EF Core will no longer know about this collection. If the property is left on `Frequency`, EF Core will try to create a shadow FK relationship for it and generate an unwanted migration.
**Why it happens:** EF Core by convention tries to map any `ICollection<T>` navigation property to a FK relationship.
**How to avoid:** Remove `Transactions` from `Frequency` and replace with `public ICollection<RecurringTransaction> RecurringTransactions { get; set; } = new List<RecurringTransaction>()`. The `RecurringTransactionConfiguration` references `WithMany(f => f.RecurringTransactions)`.
**Warning signs:** Generated migration includes an unexpected `AlterTable` or new FK on `Frequencies`.

### Pitfall 3: Category entity missing RecurringTransactions nav property
**What goes wrong:** `RecurringTransactionConfiguration` calls `.WithMany(c => c.RecurringTransactions)` but `Category.cs` doesn't have that property — compile error.
**How to avoid:** Add `public ICollection<RecurringTransaction> RecurringTransactions { get; set; } = new List<RecurringTransaction>()` to `Category.cs`.

### Pitfall 4: Application layer compilation failures after entity changes
**What goes wrong:** Removing `Transaction.FrequencyId` causes compile errors in 7 application-layer files that reference this property. The build will fail before migration tooling can run.
**Files to update:**
1. `CreateTransactionDto.cs` — remove `FrequencyId` property
2. `UpdateTransactionDto.cs` — remove `FrequencyId` property
3. `TransactionResponseDto.cs` — remove `FrequencyId`/`FrequencyName` properties and their mapping
4. `CreateTransactionCommandHandler.cs` — remove `FrequencyId = request.Dto.FrequencyId`
5. `TransactionService.cs` — remove `FrequencyId = dto.FrequencyId` in `UpdateTransactionAsync`
6. `TransactionRepository.cs` — remove `.Include(x => x.Frequency)` (×2 uses) and `entity.FrequencyId = transaction.FrequencyId`
7. Test files: `CreateTransactionCommandHandlerTests.cs`, `TransactionsApiIntegrationTests.cs` — remove `FrequencyId = null` from DTO instantiations

**How to avoid:** Update all application-layer files BEFORE running `dotnet build` to verify clean compilation, then generate the migration.

### Pitfall 5: Migration data step must precede FK/column drop
**What goes wrong:** EF Core generates `DropForeignKey` before `DropColumn` (correct order), but does NOT add the `UPDATE ... SET FrequencyId = NULL` data step. If you rely on the database FK constraint's ON DELETE SET NULL cascade to null out data — that only fires when the *referenced* Frequency row is deleted, not when the FK column is removed.
**How to avoid:** Manually add `migrationBuilder.Sql("UPDATE [Transactions] SET [FrequencyId] = NULL WHERE [FrequencyId] IS NOT NULL")` as the very first statement in `Up()`, before any EF-generated DDL.

### Pitfall 6: `required` keyword mismatch on required nav props
**What goes wrong:** The existing `Transaction.Category` is declared as `public required Category Category`. If `RecurringTransaction` uses the same pattern for `Category` and `Frequency`, but then `CreateTransactionCommandHandler` creates a `RecurringTransaction` without setting them, you get a nullable reference warning or runtime null in navigation properties.
**How to avoid:** Mark `Category` and `Frequency` on `RecurringTransaction` as `required` (matching D-03's "required" FK semantics). The Application layer will need to handle loading relations via `GetByIdAsync`. Do not use `null!` suppression unless the entity is immediately fetched from DB.
